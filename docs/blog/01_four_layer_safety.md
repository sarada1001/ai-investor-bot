# LLMトレードボットに四層安全装置を実装した話

> 個人開発している米国株スイングトレードAI「ai-investor-bot」の安全設計と、
> その設計を"正確に説明し続けること"の難しさについて。

## なぜ実弾トレードbotに複数の安全機構が必要か

LLMに株の売買判断をさせるシステムを個人で作っている。6体のエージェントが合議してBUY/HOLDを決め、
条件を満たせばAlpaca経由で実際に発注する。

一番怖いのは「LLMの判断ミス」そのものより、**判断ミスがそのまま損失に直結する経路が1本しかない
状態**だと思っている。LLMは間違えるし、プロンプトのバグも起きる。だから「LLMの判断が正しいこと」に
賭けるのではなく、「どれだけ間違えても被害が一定以上に広がらないこと」を、判断ロジックとは別に
機械的に保証する層を積むことにした。単一障害点を作らない、という設計思想である。

発注経路には独立した5つの安全機構がある。今回はその設計と、ドキュメント化の過程で見つけた
「設計と説明のズレ」について書く。

## 5つの安全機構

- **TradeGuard** — 日次BUY上限・同時保有銘柄数の上限で、発注の頻度と規模そのものを制限する。
  「1銘柄あたりの最大ポジション比率」という項目もあるが、これは後述の理由で現在は事実上無効。
- **CircuitBreaker** — ポートフォリオ全体のドローダウンを監視し、閾値超過で新規BUYを自動停止する。
  当日の下落と累計の下落でトリップを2段階に分け、軽度（翌日自動リセット）と重度（手動リセットのみ）
  を区別している。
- **LiveTradingGate** — Paper（仮想資金）とLive（実資金）を切り替えるゲート。誤ってPaperのつもりで
  Live発注してしまう事故を防ぐための専用レイヤー。
- **CriticAgent** — 数値ルールではなく、ManagerAgentの推論内容をRAGで検索した過去の失敗事例と
  照合し、判断ロジックそのものを監査するLLM層。「過去の成功体験だけを根拠にした介入」を明示的に
  禁止するルールを入れ、後知恵バイアスを防いでいる。
- **AuditAgent** — 各エージェントの勝率を継続監視し、取引数20件超で勝率40%未満なら`SUSPENDED`にして
  最終スコアへの重みをゼロにする。50%まで回復すれば復帰。「発注を止める」のではなく「発言力を落とす」
  機構という点で他4つと性質が異なる。

## 核となるエピソード：ドキュメントが実装を裏切っていた

就活ポートフォリオ用に安全設計の技術ドキュメントを書くことになり、READMEを写すのではなく
`tools/live_trading_gate.py` と `tools/trade_guard.py` のソースを直接読み直した。

読んで驚いた。READMEには「ライブ取引には24時間有効の同意ファイルと、手入力の確認ウィザードが必須」
「1銘柄の最大ポジション比率は口座の20%」と書いてあった。しかし実際の`check()`——発注可否を最終
判定する関数——は、同意ファイルも24時間の有効期限も一切参照していなかった。ライブモードで
`.env`にAPIキーが設定されてさえいれば発注が許可される実装になっており、ポジション比率の上限値も
`0.20`から`1.0`（実質無制限）に変わっていた。

コミット履歴を辿ると、1ヶ月ほど前に「TradeGuardの緩和とLiveTradingGateの完全自動化」という
コミットがあった。無人cron運用のために意図して行った変更だとメッセージから分かる。日次の
手動再認証は、人間が寝ている間に自動で回るスケジューラー運用とは相容れない。だから「日次の
人間の再承認」を「`.env`にライブキーを設定するという一度きりの意思表明」に置き換えた——これ
自体は理解できる判断だ。問題は、**この変更のタイミングでREADMEが更新されなかった**ことにある。

原因はシンプルで、コードの変更とドキュメントの更新が同じレビュープロセスに乗っていなかった
からだと思う。個人開発ではレビュアーが自分しかいないので、変更の影響がドキュメントまで及んで
いるかを追う強制力がない。もしREADMEの記述をそのまま新ドキュメントに転記していたら、この
乖離には一生気づかなかった。一次情報（コード）を確認せず、二次情報（過去のドキュメント）を
信じて再生産していたら、誤った安全設計の説明を"検証済み"の顔で世に出すところだった。

## 現状の実際の防御態勢

1. **LiveTradingGate** — 実質`.env`設定のみで有効化される本番ゲート。24時間ごとの人間の再承認は
   もう存在せず、ライブ/ペーパーの切り替えは`ALPACA_PAPER_TRADING`という環境変数1つに実質集約。
2. **TradeGuard** — 比率上限は撤廃済み。現在の主な制約は日次BUY上限と同時保有銘柄数のみで、
   単一銘柄への集中リスクを機械的に防ぐ機構はこのレイヤーには存在しない。
3. **CircuitBreaker** — 変更なし。①②の防御が実質縮小した今、最も重要な最終防衛ラインになっている。

「5つあるから安全」ではなく、そのうちいくつかは設計変更で役割が変化していることを正確に把握して
いるかどうかが、実運用上は重要だと思っている。

## まとめ

安全機構を実装することと、その説明が正確であり続けることは別の問題だ。前者は一度作れば動き続けるが、
後者は継続的なメンテナンスなしには必ず劣化する。とくに一人開発では「コードは変えたが説明は
変えていない」状態に気づく機会が構造的に少ない。

今回、トレードロジックとは直接関係のないドキュメント執筆作業が、結果的に実装とドキュメントの
乖離を発見するきっかけになった。書く行為そのものが、実装を検証する強制関数として機能した——
これが今回の一番の学びだった。
