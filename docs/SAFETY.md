# 安全装置設計ドキュメント（4層防御）

> 対象コード: `tools/live_trading_gate.py`, `tools/trade_guard.py`, `tools/circuit_breaker.py`, `tools/critic_agent.py`
> 作成日: 2026-07-02　｜　このドキュメントは実装を直接読んで作成した現状記録です（`docs/gen_test_report.py`同様、コードを一次情報とする）。

## 0. 要旨

本システムは実弾（Live/Paper）自動売買を伴うため、発注経路に**4層の独立した安全装置**を配置している。
重要な設計上の事実として、**LiveTradingGateとTradeGuardは2026-06-03のコミット `d6f7bd1`
（「TradeGuardの緩和とLiveTradingGateの完全自動化」）で意図的に自動化・緩和されており、
README等の初期ドキュメントに残っていた「24時間手動同意」「1銘柄20%上限」という記述は現在の挙動と一致しない。**
本ドキュメントは実装を再確認し、**現状の挙動**と**変更前の設計意図**の両方を明記する。

---

## 1. 全体構成

```
発注フロー
  │
  ├─① LiveTradingGate  … ライブ/ペーパーの切替ゲート
  ├─② TradeGuard        … 発注頻度・保有数・比率のガードレール
  ├─③ CircuitBreaker    … ドローダウン自動停止
  └─④ CriticAgent       … LLMによる独立監査（発注直前のAPPROVE/OVERRIDE）
```

4層のうち①〜③は「発注してよいか」の機械的判定、④は「この判断は過去の教訓に照らして妥当か」という
推論レベルの監査であり、性質が異なる（③までは数値ルール、④のみLLM判断）。

## 2. ① LiveTradingGate（`tools/live_trading_gate.py`）

### 現状の挙動（2026-06-03以降）

`check()` は以下のロジックのみで判定する:

| ステップ | 判定 |
|---|---|
| 1 | `ALPACA_PAPER_TRADING` が `true`（デフォルト）→ 常に許可（ペーパーは無条件安全） |
| 2 | `false`（ライブ）の場合、`.env` に `APCA_API_KEY_ID` が設定されているか |
| 3 | 設定されていれば **自動的に許可**（`allowed=True`） |

同意ファイル（`data/live_trading_enabled.json`）・24時間の有効期限・`enable_wizard()` による
`"CONFIRM LIVE TRADING"` 入力確認は、**コード上は現存するが `check()` からは一切参照されない**
（コード内コメント: 「旧来の手動認証ウィザード（--enable-live）は後方互換のため残存するが、
check() による発注判定には使用しない」）。

### 変更前の設計意図（〜2026-06-02）

- ライブ取引を有効にするには、`python main.py --enable-live` で**インタラクティブウィザード**を実行し、
  `"CONFIRM LIVE TRADING"` という固定文字列を手入力する必要があった。
- 有効化から**24時間で自動失効**し、取引日ごとに再認証が必要だった。
- 同意ファイルの `key_suffix` と実際のAPIキー末尾4桁が一致しているかも照合していた。

### 自動化の理由（推定される設計判断）

本システムはスケジューラーノード（`uema2lab-search`）上でcronによる**無人運用**を前提にしている。
24時間ごとの手動再認証は無人cron運用と根本的に相容れないため、「日次の人間介入」ではなく
「`.env` へのAPIキー設定」という**インフラ側の意図表明**に安全確保の重心を移した設計変更と考えられる
（`.env` に本番キーを置くこと自体が、既に人間の明示的な意思決定である）。

### この設計変更が意味するリスクの所在

- ライブ/ペーパーの切替は事実上 **`ALPACA_PAPER_TRADING` 環境変数1つ**に集約されている。
- 従って「誤ってこのフラグを `false` にしたまま`.env`にライブAPIキーを設定してcronを回す」ことが
  唯一にして最大の誤操作リスクになる。24h同意ファイルという「後から気づける」セーフティネットは
  もう機能していない。
- 主たる防御線は、この後段の **② TradeGuard** と **③ CircuitBreaker** に実質的にシフトしている。

## 3. ② TradeGuard（`tools/trade_guard.py`）

### 現状の挙動

`data/trade_guards.json` のデフォルト値（2026-06-03以降）:

| ガードレール | 現在値 |
|---|---|
| 日次BUY上限 | 3回/日 |
| 同時保有銘柄数上限 | 5銘柄 |
| 1銘柄あたり最大ポジション比率 | **1.0（=実質上限なし）** |

`_doc` フィールドのコメントも「1.0=上限なし相当」に書き換えられており、比率上限を意図的に外したことが
設定ファイル自体から読み取れる。

### 変更前の設計意図

同コミットの diff により、変更前は `max_position_pct: 0.20`（口座資産の20%が1銘柄あたりの上限）
だったことが確認できる。

### 現状で機能している防御

- 日次BUY回数上限（3回）と同時保有数上限（5銘柄）は変更されておらず、引き続き有効。
- ポジション比率の上限は撤廃されたため、単一銘柄への集中リスクを機械的に防ぐ機構は
  現時点でTradeGuardレイヤーには存在しない（Phase 4のRiskAgentのサイジングロジックが
  実質的な唯一の歯止めになる）。

## 4. ③ CircuitBreaker（`tools/circuit_breaker.py`）

READMEの記載と実装が一致していることを確認済み。変更なし。

| トリップ | 条件 | 効果 | 解除 |
|---|---|---|---|
| SOFT_TRIP | 当日ドローダウン ≥ -5% | 当日の新規BUY禁止 | 翌日自動リセット |
| HARD_TRIP | 高値比ドローダウン ≥ -10% | 全BUY禁止 | `manual_reset(level="hard")` のみ |

状態は `data/circuit_breaker_state.json` に永続化され、プロセス再起動後も当日中は維持される。
①②の防御線が事実上縮小した現在、**この閾値ベースの自動停止が最終防衛ラインとして最も重要**。

## 5. ④ CriticAgent（`tools/critic_agent.py`）

ManagerAgentの推論を、RAGで取得した過去の失敗事例（Reflexionログ）と照合し、`APPROVE` / `OVERRIDE` を
判定する独立監査層。

- LLMバックエンド: Ollama(llama3.1) 優先 → 接続エラー/タイムアウト時にGemini 2.0 Flashへ自動フォールバック
  → 両方失敗時は安全側の `_FALLBACK_RESPONSE` を返す（システムを止めない設計）。
- プロンプト内で「過去の含み益・過去の成功だけを根拠にOVERRIDEすることを明示的に禁止」するルール
  （Rule C: Strict OVERRIDE Criteria）が定義されており、後知恵バイアスによる過剰な介入を防いでいる。
- ①〜③が数値ルールによる機械的判定であるのに対し、④のみが「この売買判断のロジックが過去の教訓と
  矛盾していないか」を評価する定性的レイヤーである。

## 6. まとめ — 現在の実質的な防御構成

| レイヤー | 設計時の役割 | 現状の実効性 |
|---|---|---|
| LiveTradingGate | 日次手動同意による人間の最終承認 | **自動化により後退** — `.env`設定のみが歯止め |
| TradeGuard | 頻度・保有数・比率の3点防御 | 比率上限が撤廃 — 頻度・保有数の2点防御に縮小 |
| CircuitBreaker | ドローダウン自動停止 | **変更なし、現状の主防衛ライン** |
| CriticAgent | 過去教訓との整合性監査 | 変更なし、機能中 |

無人cron運用のための合理的なトレードオフとして自動化・緩和が行われた一方、
**「1銘柄への集中リスク」と「日次の人間承認」という2つの防御が実質的に失われている**のが現状である。
これは本ドキュメント作成時点（2026-07-02）の客観的事実であり、トレードロジック自体の変更提案ではない
（安全ルール上、ロジック変更は開発者の明示的指示なしに行わない）。
