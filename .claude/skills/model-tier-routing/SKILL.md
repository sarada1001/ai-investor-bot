# Model Tier Routing — モデル非依存の役割定義

本プロジェクトは複数のClaudeモデルを役割分担で使用する。ただし**特定のモデル名に
依存しない**こと。「どのモデルが動いているか」ではなく「どの階層（tier）が
利用可能か」で立ち回りを決める。モデル名は本ファイル末尾の「対応表」にのみ
記載し、モデルの追加・廃止時は対応表だけを更新する。

## Tier定義（抽象・不変）

| Tier | 定義 |
|---|---|
| **最上位tier** | 現時点で利用可能な最も高性能な推論モデル。深い推論・横断的判断を担う |
| **中位tier** | 実装向けの主力モデル。コスト効率と実装品質のバランスを担う |

## Tierごとの期待タスク

### 中位tier（実装向け）

- 仕様が既に固まっている機械的実装
- テストコード生成
- ドキュメント整形・翻訳・体裁修正
- 定型的なリファクタリング（rename、ファイル分割など）
- ログ・データファイルの集計や整形スクリプト作成

### 最上位tier（推論向け）

- アーキテクチャ判断（レイヤー構成の変更、新コンポーネントの設計）
- 研究妥当性の評価（バックテスト設計、アブレーション実験、Faithfulness評価の解釈）
- 複数リポジトリ・複数ノード（開発機/スケジューラー/GPU）横断の推論
- あいまいな要求の解釈・要件の具体化
- 品質レビュー（コードレビュー、安全性への影響評価）

## 最上位tierが利用不可の場合のフォールバック手順

1. **対応表を確認**し、最上位tierの代替（次点の高性能モデル）があればそれを使う。
2. 中位tierのみで進める場合、以下の判断は**自律実行せず、必ずユーザー確認を挟む**：
   - アーキテクチャに影響する設計判断（新規レイヤー・コンポーネント追加、依存関係の変更）
   - 研究実験の設計変更・実験結果の採否判断（「この結果を本番に反映してよいか」）
   - 既存ドキュメント・コードの大規模な書き換え（削除・統合を伴うもの）
   - トレードオフが伴う品質判断（性能 vs 安全性、コスト vs 精度）
3. 中位tierのみで**進めてよい**作業：仕様確定済みの実装、テスト追加、
   ドキュメント整形、対応表の更新など、上記「中位tierの期待タスク」の範囲。
4. 保留した判断は、判断内容・保留理由を明示してユーザーに提示する。

## Tierに関わらず不変の制約（絶対厳守）

どのtierで動作していても、以下は**一切変更しない**：

- 本番トレーディングロジック（`engine/`, `agents/`, `skills/` の売買判断コード）
- Safety機構（TradeGuard / CircuitBreaker / LiveTradingGate / AuditAgent / CriticAgent）
- State files（`bbs/`, `data/portfolio.json`, `data/trade_guard_state.json`,
  `data/agent_status.json` などの実行時状態）
- Credentials（`.env`, APIキー）

これらへの変更が必要に見える場合も、tierを問わず必ずユーザーの明示的な承認を得る。

## 対応表（ここだけ更新すればよい）

モデルのリリース・廃止・利用不可時は、この表**のみ**を更新する。
本ファイルの他のセクションおよび他ドキュメントにはモデル名を書かないこと。

| Tier | 現在の対応モデル | 代替（利用不可時） | 備考 |
|---|---|---|---|
| 最上位tier | Claude Fable 5 | Claude Opus 4.8 | 代替も不可なら中位tierのみ+保留手順 |
| 中位tier | Claude Sonnet 5 | Claude Haiku 4.5 | 軽量タスクはHaikuでも可 |
